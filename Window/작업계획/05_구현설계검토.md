# 초기 구현 설계 작성과 연결 검토 이력

검토일: 2026-11-24. 이 기록은 웹 UI 전환 이전의 WPF 설계 검토 이력이다. 현재 기준은 [웹 UI 전환](06_웹UI전환.md)을 따른다. 상태: 구현 설계 작성·문서와 DDL 검토 완료. 앱 코드 생성과 빌드·실행 전.

## 작성 결과

[구현 설계 폴더](../구현설계/README.md)에 기술 선정, 코드 구성, 앱 시작, 초기 자료 연결, 저장소 접근, DB 스키마, 시험 생성, 자동 저장·재개, 제출·결과, 자료 교환·복구, 화면 연결, 빌드·배포의 12개 문서를 나눠 작성했다. README는 파일을 찾는 목차다.

| 질문 | 구현 기준과 담당 |
| --- | --- |
| 어떤 기술로 만드는가 | C#·.NET 10·WPF, Microsoft.Data.Sqlite. 현재 SDK는 5.0.400만 확인되어 환경 준비 필요 |
| 자료는 어디서 읽는가 | 배포 폴더의 Assets/InitialData에 catalog와 두 learning/supplement 파일만 복사 |
| 누가 자료를 연결하는가 | AppBootstrapper → InitialDataService → LearningPackageReader → DB 쓰기 세션 |
| 화면은 무엇을 읽는가 | ViewModel → Core 서비스 → DB 읽기 세션 → 화면 DTO. 초기 JSON 직접 조회 안 함 |
| 저장 성공은 누가 결정하는가 | DbWorkQueue가 트랜잭션 COMMIT 후 결과 반환 |
| 정답은 언제 전달하는가 | 작성 DTO에서 제외하고 완료된 시험의 결과 DTO에만 포함 |
| 로그인은 필요한가 | 별도 로그인 없이 실행. 로컬 프로필 ID는 내부 기록 연결에만 사용 |

## 연결 검토에서 구체화한 내용

- 새 DB는 임시 경로에서 구조와 자료 등록을 마친 뒤 최종 경로로 전환한다. 기존 DB의 읽기·식별 실패를 새 설치로 처리하지 않는다.
- 초기 등록 표시, 로컬 프로필, 두 자료와 보충 정보의 원자적 저장을 연결했다. 이미 데이터가 있는데 등록 표시만 없으면 덮어쓰지 않는다.
- 읽기·쓰기 세션과 단일 작업 큐를 정의하고 SQL 연결을 Core와 화면에 노출하지 않게 했다. SQLite 작업은 UI 스레드 밖에서 실행한다.
- 자료 revision과 시험 revision을 구분했다. 자료 미리보기 충돌, 오래된 답변 저장, 제출 후 입력과 COMMIT 여부 불명의 재시도 경로를 정했다.
- DB의 행 제약과 서비스가 같은 트랜잭션에서 검사할 여러 행의 조건을 구분했다. 완료 상태·판정·오답 집계의 동시 확정을 유지했다.
- 복구 시 기존 화면과 작업 큐를 폐기하고 초기화 경로를 다시 수행해 과거 요청이 복구된 DB를 변경하지 않게 했다.

## 수행한 검사

문서에 적은 초기 DDL을 그대로 추출해 Python의 임시 SQLite에서 실행했다. 8개 테이블에 실제 254문항과 보충 정보를 넣고 **11개 시나리오를 통과**했다. 중복 응답과 순서, 외래 키, 상태와 오답 사유, 완료 순번, 오답 횟수, 원본 제거 후 스냅샷, 완료 롤백과 입력 원문 보존을 확인했다.

결과는 [구현 스키마 검사 결과](검증/구현스키마검사결과.json), 재실행 경로는 [검증 목차](검증/README.md)에 둔다. 문서의 로컬 경로 검사 결과도 같은 목차에서 확인한다.

이 검사는 C# 저장소나 WPF 화면의 테스트가 아니다. .NET 10 SDK 준비, NuGet 정확한 버전 고정, 기본 창 빌드·실행, Microsoft.Data.Sqlite 실제 연결과 배포 환경 검증은 [구현 계획 1단계](04_구현진행계획.md)부터 수행한다.
