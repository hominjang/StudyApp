# 자료 학습 편집 연결

상태: 2026-11-27 구현. 열람 조회와 명시적인 자료 수정을 분리하며 시험/평가 정정 명령과 섞지 않는다.

`StudyWorkspace` → `MaterialEditor` → `bridge/study.ts`의 `updateStudyMaterial` → `update_study_material` → `DbWorker` → `transfer/edit.rs`의 `MaterialEditState` 순서다. DB 1/2의 현재 연결을 쓰며 스키마 변경이나 기존 DB 전환은 없다.

| 계약 | 기준 |
| --- | --- |
| 조회 | `StudyItem.dataset_revision`으로 읽은 묶음 버전을 전달 |
| 요청 | UUID v4 request_id, 묶음/문항 ID, expected_revision, 기존 유형의 criteria, 선택 explanation |
| 허용 변경 | 단답 정답/허용 표기 또는 서술 참고 답안/핵심 내용, 해설만 수정. 질문·유형·ID·순서·활성 상태는 유지 |
| 검증 | 기존 공통 고정 공백/단답 4단어/기준 길이·개수 검증 재사용. 해설 최대 UTF-8 64 KiB. 문자열 trim/정규화 없음 |
| 저장 | 쓰기 트랜잭션 안에서 묶음 revision과 활성 문항 확인 후 대상 기준/해설·최종 자료 해시·묶음 revision을 함께 갱신. 동일 내용은 no-op |
| 보존 | 해설 이외 보충 필드·출처 원문 ID·기초 연결·다른 문항을 유지. 시험 스냅샷·응답·판정·학습 상태는 수정하지 않음 |
| 충돌 | 가져오기 또는 다른 편집으로 revision이 달라지면 MaterialConflict로 거부. 덮어쓰기 없이 입력 유지·취소 후 재조회 |

자료 해시는 가져오기와 같은 최종 자료 스냅샷 표현으로 계산한다. 편집 저장은 같은 문항의 기준과 해설만 SQL로 변경하며 전체 문항 재정렬을 하지 않는다. 편집 후 이전 가져오기 미리보기를 적용하려 하면 revision 검사에서 거부한다.

같은 앱 실행 동안 성공 request_id와 요청 해시·결과를 메모리에 보관한다. 응답 유실 후 같은 요청은 기존 결과만 반환하고, 같은 ID의 다른 내용은 RequestConflict다. 재실행 후 영구 요청 영수증은 제공하지 않으므로 새 화면은 현재 자료를 다시 조회한다.

편집을 열면 자료 선택·검색·페이지·다른 메뉴를 잠그고 종료 전 guard가 저장/취소를 요구한다. 저장 결과 미확인은 동일 payload/request_id 재시도만 허용한다. 검증/자료 충돌처럼 변경 없이 거부된 오류는 입력을 유지하며 취소·재조회가 가능하다. 저장 성공 뒤 페이지를 다시 조회해 같은 묶음의 다른 문항 revision도 갱신한다.

여러 줄 참고 답안·핵심 내용·해설은 기존 `answerText.ts`의 표시/원문 매핑을 재사용한다. 편집하지 않은 CR/CRLF를 조용히 LF로 바꾸지 않는다. 원본 JSON 파일은 쓰지 않는다. [사용 안내](../사용안내/03_정답과해설수정.md)·[검증 결과](../작업계획/20_메뉴와자료편집.md)
