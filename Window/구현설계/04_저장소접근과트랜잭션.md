# 서비스와 저장소의 접근 계약

상태: 초기 등록·자료 조회용 SQLite 연결과 전용 DB 스레드 구현. 시험·복구 작업은 이후 단계다.

## React와 Rust 경계

```typescript
invoke<ExamSessionDto>('start_exam', { request });
```

명령 인자는 request 객체로 묶고 DTO 필드는 공통 명세와 같은 snake_case를 사용한다. Rust는 serde로 역직렬화한 뒤 값과 상태를 검증한다. JS의 타입만 믿지 않는다. 조회·변경·완료를 별도 명령으로 두고 임의 SQL 실행 API는 노출하지 않는다. [공식 명령 호출 방식](https://v2.tauri.app/develop/calling-rust/)

## DB 작업 큐

application은 읽기·쓰기 작업을 `DbJob` 요청과 응답 계약으로 전달한다. DbJob은 자료 조회·시험 생성·저장·제출·완료 등 닫힌 작업 종류와 소유한 입력 값을 가진다. 명령 핸들러는 작업 결과를 await하고, infrastructure의 전용 DB 스레드가 단일 큐를 소비한다.

전용 DB 스레드가 초기화한 rusqlite 연결 하나를 소유하고 작업별 트랜잭션을 사용한다. 초기화 실패 후에는 다음 요청에서 다시 시도하며, 성공한 연결은 앱 종료까지 재사용한다. application의 트랜잭션 작업 함수가 세션을 통해 데이터를 읽고 domain 규칙을 계산한 뒤 저장한다. 세션에는 Metadata·Learners·Datasets·Exams·Progress의 조회와 변경 계약이 있으며 연결·SQL 객체는 React나 domain으로 나가지 않는다.

전용 스레드에서 동기 SQLite를 사용하고 비동기 이벤트 스레드를 막지 않는다. 세션 안에서 요청을 다시 큐에 넣거나 await하지 않는다. 모든 조회 결과는 세션 안에서 모델로 읽어 반환하고 지연된 reader를 밖으로 전달하지 않는다.

## 트랜잭션과 연결 설정

연결마다 foreign_keys=ON, synchronous=FULL, journal_mode=DELETE, busy_timeout=3000을 적용·확인한다. 읽기는 Deferred, 쓰기는 Immediate transaction으로 시작한다. COMMIT 성공 후에만 성공 DTO를 반환하고 오류·거부는 ROLLBACK 후 전달한다. 조회도 같은 큐에서 처리해 부분 결과를 노출하지 않는다.

| 작업 | 함께 확정할 범위 |
| --- | --- |
| 초기 등록 | 프로필·자료·보충·등록 표시 |
| 자료 갱신 | 자료 revision 확인·문항·보충·해시와 새 revision |
| 시험 생성 | 조건 재확인·선택과 순서·설정·전체 문항 스냅샷 |
| 진행 저장 | 상태·revision 확인과 답변·위치·saved_at |
| 제출 | 최신 답변·revision·위치와 submitted 상태·시각 |
| 완료 | 전체 판정·완료 순번·상태·학습 상태 |

출제와 재집계는 현재 자료 규모의 메모리 계산을 같은 쓰기 작업 안에서 수행한다. 파일 읽기·JSON 검증·미리보기와 사용자 확인은 트랜잭션 밖에서 수행한다.

원문 문자열은 parameter로 바인딩한다. 갱신은 ON CONFLICT DO UPDATE를 사용하며 INSERT OR REPLACE로 참조 행을 삭제하지 않는다. 이미 실행한 쓰기는 COMMIT 또는 ROLLBACK을 끝낸 뒤 결과를 전달한다. 화면 이탈과 요청 취소가 DB 쓰기를 소급 취소했다고 표시하지 않는다.

## 문자열과 정수

Rust 문자열을 정규화하지 않고 정확히 비교한다. IPC의 revision과 position·개수는 안전한 JS 정수인지 검사하고 Rust의 i64 범위에도 맞아야 한다. 완료 순번은 사용자별 DB 트랜잭션에서 부여한다. 자료 ID와 시험 ID는 문자열로 유지한다.

백업은 [rusqlite Backup API](https://docs.rs/rusqlite/latest/rusqlite/backup/index.html)를 사용하는 단일 유지보수 작업으로 구성할 예정이다. 초기 등록·조회 코드는 컴파일과 롤백·재시도를 검증했다. 시험 저장의 잠금·장애와 백업 복구 검증은 해당 기능 구현 단계에서 수행한다.
