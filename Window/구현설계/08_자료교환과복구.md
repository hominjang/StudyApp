# 자료 교환과 백업 및 복구 연결

상태: 2026-11-27 가져오기·갱신 구현. 내보내기·독립 복제·백업·복구는 아래 설계만 있고 아직 명령이 없다. 파일 교환과 DB 변경을 분리하며 DB 전체를 자료 JSON으로 취급하지 않는다. [검증 결과](../작업계획/18_배포앱자료추가.md)

## 가져오기와 갱신

React `ImportWorkspace` → `choose_import_file(kind)`가 Windows 소유 창의 파일 선택 대화상자를 전용 STA 스레드에 연다. `import_file.rs`가 선택한 파일만 각 16 MiB까지 읽고 UTF-8을 검사한다. 사용자 취소는 null이며 이전 선택을 유지한다. UI는 파일명과 읽은 내용을 보관하고 `preview_import`로 전달한다. `DbWorker`의 `ImportState`가 기존 공통 `learning_format::parse_package`로 크기·내용을 재검증한다. 학습 파일 하나와 선택적인 같은 버전/묶음의 보충 파일이 입력이다. 기존 DB 1은 JSON 1.0만, DB 2는 1.0/2.0을 지원한다. 원문·보고서·응시 기록과 미지원 버전은 학습 파일로 적용하지 않는다.

검증된 DTO는 메모리에 보존하고, 현재 자료 revision과 비교해 추가·변경·비활성화 수를 포함한 `ImportPreview`를 만든다. 적용은 미리 읽은 DTO를 사용하므로 미리보기 뒤 외부 파일의 변경이 끼어들지 않는다. 새로 파일을 선택하면 미리보기를 다시 만든다.

`apply_import(token)`은 작업 큐 안에 보존한 DTO만 사용하고 쓰기 트랜잭션에서 기존 자료 revision 또는 자료 없음 상태가 같은지 재확인한다. 다르면 `ImportConflict`로 재검토를 요청하고 덮어쓰지 않는다. 새 묶음이면 등록하고 기존 묶음이면 전체 갱신한다. 독립 복제는 후속 구현이다. 같은 앱 실행에서 성공 토큰을 재시도하면 기존 결과를 돌려주며, 앱 재실행 후 다시 파일을 선택해도 최종 내용 비교로 중복 추가하지 않는다.

기존 문항은 비활성화 후 입력 순서로 upsert한다. 생략한 보충 파일과 dataset_metadata는 기존 값을 유지한다. 제공한 보충 항목은 해당 문항의 선택 정보 전체를 교체하고, 제공하지 않은 문항의 보충 정보는 유지한다. 최종 자료와 실제 반영 후 보충 정보를 기준으로 해시를 계산하고 내용이 같으면 중복 갱신하지 않는다. 변경되면 자료 revision을 1 올린다. 시험 스냅샷과 기존 학습 상태는 수정하지 않는다.

## 내보내기

`ExportAsync(datasetId, destination)`는 하나의 읽기 세션에서 자료명과 활성 문항·보충 정보·메타데이터를 DTO로 만든다. `PackageWriter`는 DB 연결이 종료된 뒤 대상 상위 폴더의 새 임시 폴더에 UTF-8 learning/supplement JSON을 작성·검증한다. 없던 새 출력 폴더명으로 이동한 뒤에만 성공을 반환한다.

기존 폴더는 덮어쓰지 않으며 파일 내용의 ID·문항 순서·원문 문자열을 유지한다. 미응답·사용자 응시 기록은 이 출력에 포함하지 않는다. 적용 화면 흐름은 [자료 교환 화면](../화면흐름/01_1_자료교환.md)을 따른다.

## 백업과 DB 구조 변경

`BackupManager`는 쓰기 큐에 예약한 유지보수 작업에서 rusqlite의 Backup API로 새 백업을 생성한다. 완료 후 `integrity_check`, `foreign_key_check`, 앱 식별과 구조 버전을 확인하고 정상 백업 목록에 등록한다. 백업 API가 다른 쓰기를 막을 수 있으므로 UI 스레드에서 실행하지 않는다. [rusqlite 백업 API](https://docs.rs/rusqlite/latest/rusqlite/backup/index.html)

`DatabaseInitializer`는 알려진 이전 버전만 백업 후 순차 migration한다. 각 버전의 변경과 db_schema_version 갱신을 같은 트랜잭션으로 수행한다. 구조 버전 1의 첫 배포에는 이전 앱 DB를 가정한 임의 변환을 넣지 않는다. 이후 변경마다 실제 이전 버전 fixture를 추가한다.

## 복구의 실행 경계

1. 사용자가 백업과 복구 적용을 선택하면 최신 기록이 백업 시점으로 돌아감을 알린다. 학습 화면과 새 DB 요청을 중단하고 작업 큐를 비운다.
2. 백업을 앱 데이터 폴더의 새 임시 복구 파일로 복사한 뒤 그 사본의 식별·지원 버전·무결성·외래 키와 시험 상태 일관성을 검사한다. 미지원·불완전 백업은 적용하지 않는다.
3. 모든 DB 연결을 닫은 상태에서 같은 볼륨의 준비된 복구 파일로 원본을 교체한다. 기존 파일은 별도 복구 전 사본으로 보존한다. 실패 시 원본을 유지하거나 그 사본으로 되돌린다.
4. 기존 React 기능 상태과 DB 작업 큐를 폐기하고 앱 초기화 경로를 다시 수행한다. 완료 기록에서 학습 상태를 재계산·검사한 뒤 정상 화면으로 돌아간다. 이전 화면의 지연된 저장 요청은 새 실행 세대에 적용하지 않는다.

읽기 실패 화면에서도 이 복구 경로에 접근할 수 있게 한다. 복구는 DB 초기화 기능이 아니며 기록을 임의로 새로 생성하지 않는다. 원칙은 [백업과 구조 변경](../저장방식/05_백업과구조변경.md)을 따른다.

서비스의 Async 메서드 표기는 후속 사용 사례의 책임을 나타낸다. 실제 React 호출은 [Rust 명령 표](09_화면연결과오류처리.md)를 사용하고, DB·규칙 처리는 Rust 안에서 수행한다. 가져오기 두 명령 외의 내보내기·백업·복구 명령은 다음 단계다.
